# Platform Acceptance Tests

Scope: PLTREQ-001 through PLTREQ-024.
Motivation: PLTREQs were closed on documentation review, not running tests.
This document designs the tests that verify platform behavior independently
of documentation claims.

DANREQ acceptance tests are explicitly out of scope here; they will be
designed separately when that work begins.

Test results (PASS/FAIL/BLOCKED) are reported in a separate report document
that does not yet exist. This document contains design only.

## Environment strategy

Two pre-built Docker images:

- **`cold`** — pristine official NRP/InvenioRDM release, no patches. Used only by
  PLT-021-a. The NRP source mounts as a volume; the build runs inside the
  container as part of the test.
- **`patched`** — minimal patch set applied on top of cold, pre-built into the
  image. All other tests run against `patched`.

PLT-021-a is a diagnostic, not a conventional pass/fail test. **FAIL** means the
current patch set is still required; **PASS** means a patch can be retired. This
test should be re-run against each new NRP upstream release to drive patch-set
minimization — the long-term expectation is that the minimal patch set converges
to zero as upstream issues are resolved.

Test data isolation is handled at runtime: a session-scoped pytest fixture wipes
and reseeds the database at the start of each full run; individual tests use
unique prefixes (e.g., `plt_007a_<uuid>`) for all created identifiers to prevent
cross-test state interference.

## Publish workflow convention

Publishing in this instance goes through a `WorkflowRequest`, not a direct state
transition. Curators and owners receive `AutoApprove`, so their publish requests
resolve immediately. **All tests that require a published record must use a
community curator or owner token.** Tests that involve a plain submitter
publishing will appear to succeed at the request-submission step but the record
will sit in `submitted` state, not `published`.

Deletion of a published record similarly uses the `delete_published_record`
request (curator/owner → AutoApprove → `deleted`), not a direct `DELETE` call.

**Environment:** cold (the only cold test)

This is the diagnostic signal that the patch set remains necessary. Record which specific checks fail — this is the evidence for which patches are still load-bearing and which can be dropped.
